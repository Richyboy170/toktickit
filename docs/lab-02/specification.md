# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a professional, responsive Requester experience in which a selected Development Requester can create an IT support Ticket, find and inspect only their own Tickets, and manage permitted Attachments. The Development Requester context is a Lab 2 test mechanism, not authentication.

## 2. Stakeholder Request Interpretation

Lab 2 adds four connected workflows: Development Requester selection, Create Ticket, My Tickets, and Requester Ticket Detail with Attachment management. PostgreSQL remains the source of truth. The frontend must make loading, success, validation, empty, no-results, and safe failure states visible without losing useful user input.

## 3. Scope

### Included

- Active Development Requester selection and switching.
- Active Category and Related System reference data.
- Ticket creation with a backend-generated official Ticket Number.
- Requester-owned search, filters, sorting, pagination, and Ticket Detail.
- Attachment upload, metadata, preview/download, and soft removal.
- Zen Green reusable UI, accessibility, responsive layouts, tests, and evidence.

### Excluded

- Passwords, sessions, tokens, real login, authorization, and role management.
- IT Staff queues, claiming, assignment, IT Priority changes, and staff controls.
- Comments, Internal Notes, Actions Taken, and all post-creation status transitions.
- Resolution, closure, reopening, cancellation, and administration.

## 4. Functional Requirements

- **FR-01:** The application shall load only active Development Requesters from PostgreSQL before requester-owned screens can be used.
- **FR-02:** The application shall store the selected Development Requester for the browser tab session and show the selected name in the application shell.
- **FR-03:** Changing Requester shall clear requester-specific UI state and reload data for the newly selected Requester.
- **FR-04:** The Create Ticket screen shall load active Categories and Related Systems from PostgreSQL.
- **FR-05:** A Requester shall create a Ticket with Category, Related System, Summary, Requested Priority, and Description.
- **FR-06:** The backend shall generate and return the official Ticket Number and Ticket Date.
- **FR-07:** The Create Ticket flow shall validate permitted Attachments before upload and report partial upload failures without deleting the created Ticket.
- **FR-08:** My Tickets shall show only the current Development Requester's Tickets.
- **FR-09:** My Tickets shall support search, Category/System/Priority/Status filters, sorting, and pagination.
- **FR-10:** A Requester shall open a read-only detail view for an owned Ticket.
- **FR-11:** A Requester shall list, preview where supported, and download active owned Attachments.
- **FR-12:** A Requester shall add a permitted Attachment to an owned Ticket while the active limit is not exceeded.
- **FR-13:** A Requester shall soft-remove an active owned Attachment after confirmation and a valid reason.
- **FR-14:** The application shall display retained metadata for removed Attachments while blocking their content.
- **FR-15:** Every screen shall provide accessible loading, empty, no-results, validation, success, and safe failure feedback as applicable.
- **FR-16:** Desktop, tablet, and mobile layouts shall remain usable without horizontal page scrolling.

## 5. Business Rules

- **BR-01:** The official Ticket Number is generated by the backend and is unique.
- **BR-02:** Ticket Numbers use `TKT-YYYYMMDD-XXXXXXXX`, where the date is the UTC creation date and the suffix is eight uppercase hexadecimal characters.
- **BR-03:** A new Ticket begins with Current Status `NEW` and the database creation time is its Ticket Date.
- **BR-04:** Lab 2 uses a Development Requester selector for testing; it is not secure authentication.
- **BR-05:** Only active Requesters appear in the selector or may create/access Tickets.
- **BR-06:** The selection is stored in `sessionStorage`; closing the tab ends the selection.
- **BR-07:** Requester-scoped API calls carry `X-Development-Requester-Id`; the backend validates the active Requester on every call.
- **BR-08:** Missing or inactive requester context cannot access requester-owned screens or data.
- **BR-09:** Cross-requester Ticket or Attachment access returns the same `404` shape as a missing resource.
- **BR-10:** Category and Related System selections must reference active database rows.
- **BR-11:** Requested Priority is one of `LOW`, `MEDIUM`, `HIGH`, or `URGENT`.
- **BR-12:** Summary is trimmed, required, and 5-120 characters.
- **BR-13:** Description is trimmed, required, and 10-5000 characters.
- **BR-14:** A client-generated UUID submission token is unique per Requester and prevents duplicate Tickets.
- **BR-15:** The first valid creation returns `201`; replaying the same token returns the original Ticket with `200` and `replayed: true`.
- **BR-16:** The Submit button is busy and disabled while creation is in progress.
- **BR-17:** Validation or server failure preserves editable form values and valid selected files.
- **BR-18:** Search is case-insensitive across Ticket Number, Summary, and Description.
- **BR-19:** Filters support Category, Related System, Requested Priority, and Current Status.
- **BR-20:** Sort fields are `createdAt`, `updatedAt`, `ticketNumber`, and `summary`; order is `asc` or `desc`.
- **BR-21:** Default ordering is `updatedAt desc`, then `id desc` for stability.
- **BR-22:** Pages are one-based; page sizes are 5, 10, 20, or 50 and default to 10.
- **BR-23:** Invalid list parameters return `400`; a page beyond the last page returns an empty item list with valid metadata.
- **BR-24:** An unfiltered zero total is an empty state; zero matches after search/filtering is a no-results state.
- **BR-25:** Allowed Attachment types are JPEG/JPG, PNG, WEBP, and PDF.
- **BR-26:** Attachment extension, declared MIME type, and detected file signature must agree.
- **BR-27:** Each Attachment is at most 5 MiB (5,242,880 bytes), including exactly-at-limit files.
- **BR-28:** A Ticket has at most five active Attachments; removed Attachments do not count toward the limit.
- **BR-29:** Attachment bytes and metadata are stored in PostgreSQL; filenames are sanitized for display/download and never used as storage paths.
- **BR-30:** Ticket creation completes before selected files upload one at a time; a failed upload does not roll back the Ticket or prior successful uploads.
- **BR-31:** Removal requires confirmation and a trimmed reason of 3-200 characters.
- **BR-32:** Soft removal records `removedAt`, `removalReason`, and `removedByRequesterId` while retaining the Attachment row.
- **BR-33:** Removed Attachments remain visible as metadata but cannot be previewed or downloaded; an owned removed download returns `410`.
- **BR-34:** Active image Attachments may preview inline; PDFs open through a fetched blob URL; every active Attachment remains downloadable.
- **BR-35:** Unexpected errors are logged server-side and return a safe message without stack traces or database details.
- **BR-36:** Lab 3 will replace the development requester header with authenticated identity without changing Ticket ownership relationships.

## 6. UI Specification Summary

The application uses routes `/select-requester`, `/tickets`, `/tickets/new`, and `/tickets/:ticketId`. The Zen Green application shell and reusable controls follow [ui-spec.md](./ui-spec.md). Desktop uses multi-column forms and a Ticket table; mobile stacks form fields and uses Ticket cards. Read-only values, editable values, errors, warnings, success, focus, disabled, and busy states are visually and textually distinct.

## 7. Data Changes

- `DevelopmentRequester`: integer ID, unique email, display name, active flag, timestamps, and owned Tickets.
- `Category`: existing integer ID/name plus active flag, updated timestamp, and Tickets.
- `RelatedSystem`: integer ID, unique name, active flag, timestamps, and Tickets.
- `Ticket`: integer ID, unique Ticket Number, Requester/Category/System foreign keys, Summary, Description, Requested Priority, Current Status, submission token, timestamps, and Attachments.
- `Attachment`: integer ID, Ticket foreign key, sanitized original name, MIME type, byte size, PostgreSQL binary content, upload timestamp, nullable removal metadata, and remover foreign key.
- Unique `(requesterId, submissionToken)` prevents duplicate submission. Indexes support Requester/date lists, filters, ownership lookup, and active Attachment counting.

**Decision justification:** PostgreSQL binary storage keeps Attachment ownership, bytes, and soft-removal state in one transactional system and avoids unsafe filesystem paths. The fixed maximum of five 5 MiB files per Ticket bounds the MVP storage cost. A future object-storage migration can retain the metadata contract and replace only the content field.

## 8. API Contract

All endpoints, shapes, statuses, ownership behavior, query rules, and safe errors are defined in [api-spec.md](./api-spec.md). The development Requester header is deliberately visible and documented as insecure test context.

## 9. Acceptance Criteria

- **AC-01:** Given active Requesters, when the selection screen loads, then they appear and inactive Requesters do not.
- **AC-02:** Given no selected Requester, when a requester-owned route opens, then the selection screen is shown with the Lab 2 testing explanation.
- **AC-03:** Given Requester A is selected, when Requester B is selected, then A-specific data disappears and B-specific data reloads.
- **AC-04:** Given valid Ticket data, when submitted, then exactly one `NEW` Ticket is saved and its official Ticket Number is displayed.
- **AC-05:** Given invalid Ticket data, when submitted, then field-level errors appear and no Ticket is saved.
- **AC-06:** Given the same submission token is sent twice, then only one Ticket exists and the replay returns that Ticket.
- **AC-07:** Given reference loading or creation fails, then a safe error appears and entered form data remains.
- **AC-08:** Given valid and invalid selected files, then invalid files are rejected clearly and valid files remain eligible to upload.
- **AC-09:** Given Ticket creation succeeds but an Attachment upload fails, then the Ticket remains, its number is displayed, and the failed file can be retried.
- **AC-10:** Given Requester A, when My Tickets loads, then only A's Tickets and correct pagination metadata are returned.
- **AC-11:** Given search, filter, and sort parameters, then the matching owned Tickets appear in the documented stable order.
- **AC-12:** Given no owned Tickets versus no filtered matches, then distinct empty and no-results states appear.
- **AC-13:** Given Requester B requests A's Ticket directly, then no Ticket data is returned and the response is `404`.
- **AC-14:** Given an owned Ticket, when detail opens, then all Ticket fields are read-only and active/removed Attachment metadata is correct.
- **AC-15:** Given a permitted file within size/count limits, when uploaded, then it is stored and can be previewed/downloaded by its owner.
- **AC-16:** Given an invalid type, oversized file, or sixth active file, then upload is rejected without creating an Attachment row.
- **AC-17:** Given a valid reason and confirmation, when an owned Attachment is removed, then metadata remains and content access returns `410`.
- **AC-18:** Given cross-requester Attachment metadata, upload, removal, or download access, then the response is `404` and no change occurs.
- **AC-19:** Given keyboard-only use, then navigation, controls, validation, dialogs, and focus indicators remain operable and understandable.
- **AC-20:** Given desktop, tablet, and mobile viewports, then required content remains readable with no clipping, overlap, hidden actions, or horizontal page scrolling.

## 10. Definition of Done

### Product completion

- All FRs, BRs, and ACs are implemented and traceable to passing tests.
- Migrations and idempotent seed run successfully on a clean database.
- Client/server builds and unit, API, UI, responsive, and E2E tests pass with none skipped.
- Ownership, validation, boundary, duplicate, loading, failure, and soft-removal cases are verified.
- UI matches `ui-spec.md` at desktop, tablet, and mobile sizes and passes the visual checklist.
- README, API, setup, seed, migration, and test instructions match the implementation.
- No secrets, Attachment bytes, generated builds, or dependencies are committed accidentally.

### Course delivery

- Issues #13-#20 use the required Project states and one branch per Issue.
- Every feature enters `lab2-staging` through a peer-reviewed merge-commit PR.
- The peer reviewer, not the author/agent, performs merges.
- Integration tests pass on staging before the single release PR to `main`.
- `reviewer.md`, `ai-use.md`, screenshots, links, and Answer Part 1-9 evidence are genuine and current.

## 11. Assumptions and Decisions

- Times are stored in UTC and displayed in the browser locale.
- IDs are integers internally; Ticket Number is the public identifier.
- Attachment binary storage is acceptable for this bounded course MVP.
- This contract records the decisions approved when the student requested implementation of the agreed Lab 2 plan on 20 August 2026.
